# Operations Automated Roadmap

## North star

Create a practical, AI-led and human-controlled methodology that helps an individual, team or organisation understand, govern and improve operations as connected systems and become ready for justified automation, AI assistance and bounded agentic operation.

The methodology should return useful analysis, options, recommendations, implementation routes and retained learning without requiring the user to be a developer or methodology specialist.

Operations Automated should improve itself through the same evidence-led approach: AI manages authorised feedback, analysis, drafting, checks and routine repository execution; Jamie retains control over meaning, authority, release and consequence.

## Three workstreams developed in tandem

| Workstream | Purpose | Immediate evidence |
|---|---|---|
| Methodology | Define the complete operational system, readiness path, OPERATE cycle and useful outputs | Can it produce a useful assessment and improvement route? |
| Evolution system | Turn feedback and outcomes into AI-drafted, human-approved methodology releases | Can Jamie understand and control a change without developer work? |
| Delivery system | Apply the method through facilitated AI before rebuilding a product | Does the user receive useful analysis throughout the journey? |

Commercial validation follows evidence from these workstreams; it does not determine the methodology's values or approve external publication.

## Milestones and human control points

| Milestone | Main work | Evidence required | Jamie's decision |
|---|---|---|---|
| 0. Architecture reset | Review v0.4 architecture, governance, output and delivery proposals | Scope is understandable and important omissions are visible | Approve, revise or reject the basis for internal development |
| 1. Manual method-and-evolution MVP | Apply the method to Operations Automated and process resulting feedback through GitHub | The method creates outputs and the update loop creates a clear decision packet | Confirm whether the tandem approach is useful |
| 2. Facilitated operational cases | Run at least two real, non-confidential cases with different scopes or work types | Useful findings, readiness decisions, implementation routes and retained feedback | Choose the modules and gaps to develop next |
| 3. Product definition | Define the smallest delivery product from observed user value | Validated journey, output contract, information boundary, success measures and alternatives | Approve product scope and any AI or data connection |
| 4. Private AI delivery product | Build the simplest secure product that reproduces the facilitated value | Reliable analysis, provenance, human gates, recovery and retained records | Approve bounded private use |
| 5. Connected evolution | Add approved feedback sources, evidence storage and notifications | Consent, security, signal quality, decision usefulness and removal routes | Approve each connection and delegated action |
| 6. Commercial and publication validation | Test audience, demand, willingness to pay and support model | Repeatable user value and controlled publication plan | Approve external release, pricing and communication |

The methodology and evolution loop continue throughout every milestone. Evidence may cause a return to an earlier milestone or a decision not to build a product.

Milestone 0 was approved for internal validation by Jamie Peppard on 2026-07-20 through PR #6.

## Application decision

The v0.4 decision parks the original application and preserves it as a learning experiment. Later governance-workbench and connected-service prototypes are additional evidence, not an approved production direction. Do not merge, deploy or commercialise them merely because they have been built.

Product work should resume from validated user outputs, not from the current page structure.

## What Jamie needs to do

Jamie does not need to edit files, design the application or operate GitHub manually.

During internal validation Jamie provides operational context, confirms value and constraints, and makes decisions where authority or consequence matters. AI leads assessment, repository work, output production and proposal execution.

Jamie's next participation is a short response to a daily challenge or a question posed to the methodology. Jamie may skip a check-in and should not need to design the method, repository change or product journey.

## Connections and technology

The manual method-and-evolution MVP requires no new external connection.

Before any AI provider, feedback form, analytics service, database, notification channel or business system is connected, AI should explain:

- The outcome the connection enables
- Information sent, received, stored and deleted
- Permissions and authority represented
- Security, privacy, legal and ethical considerations
- Failure, recovery and removal routes
- Cost and credible alternatives

Jamie must explicitly approve each consequential connection.

## Success measures

- The methodology addresses operations as connected systems rather than isolated process steps.
- A user can start from an ordinary-language problem and receive a useful partial assessment immediately.
- The method distinguishes operational, automation, AI and agentic readiness using evidence rather than aspiration.
- Every material recommendation exposes uncertainty, trade-offs, authority and a next action.
- Human judgement and approval cannot be inferred or bypassed.
- Real cases produce implementation artefacts and retained learning rather than paperwork alone.
- Feedback is traceable through proposal, decision, release and outcome review.
- Each cycle makes the methodology and its delivery more useful without silently expanding AI authority.
