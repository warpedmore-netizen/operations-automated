# Proof-of-concept test plan

## Purpose

Test whether one person can create, challenge, govern, release and maintain a fictional operational documentation estate from scratch, and whether the resulting connected records provide a credible knowledge base for later AI assistance and external publishing.

This plan uses only fictional demonstration information. It does not test regulatory compliance or authorise a live external connection.

## Primary test journey: create from scratch

1. Select a document type and choose **Create from scratch**.
2. Answer the universal ownership, purpose, authority, review, effective-date and classification questions.
3. Answer document-specific follow-up questions produced from remaining gaps.
4. Review proposed obligations, policy statements, controls, responsibilities, procedure steps and evidence requirements.
5. Accept, amend or reject every candidate.
6. Assemble accepted candidates and inspect the connected draft graph and generated policy/procedure, confirming both remain unapproved.
7. Run the fictional prolonged-outage scenario.
8. Convert observations into findings and propose controlled changes.
9. Confirm the suggested change class, or escalate it.
10. Attempt authorised and unauthorised downgrades.
11. Approve and release the valid change.
12. Confirm previous versions, notifications, validation requirements and audit events.
13. Publish the approved view to mock Confluence and Notion.
14. Simulate a remote edit, detect drift and confirm overwrite protection.

## Secondary intake demonstrations

Create fictional examples for:

- a Word policy with headings, paragraphs and a table;
- a Google Docs procedure referenced by document ID;
- a Confluence runbook referenced by page ID;
- a Notion standard referenced by page ID;
- an organisation with no existing document using guided creation.

Until live connections are approved, remote retrieval is mocked and clearly labelled.

## Test themes and evidence

| Theme | Evidence of success |
|---|---|
| Flexible entry | Document type is independent of starting route and source platform |
| Useful guidance | Baseline and gap questions are understandable and avoid unnecessary repetition |
| Human control | Suggestions never become controlled content without acceptance |
| Traceability | Generated wording traces to source, answers, objects, findings and releases |
| Proportionality | Change class produces an understandable approval and notification route |
| Authority | Anyone can escalate; only delegated roles can downgrade with justification |
| Version control | Approved records are superseded, never overwritten |
| Publication | Only approved releases publish and platform translations preserve provenance |
| Drift | External changes are detected and conflicting publication stops |
| Recoverability | Restart and state migration preserve prior governed history |

## Fictional demonstration estate

Build examples across several operating contexts to avoid tailoring the design only to banking incident management:

1. Incident Management — prolonged digital-service outage.
2. Supplier Management — failure of a critical outsourced service.
3. Customer Complaints — vulnerable-customer escalation gap.
4. Change Management — emergency production change with incomplete evidence.
5. Business Continuity — loss of a primary workplace or collaboration service.

Each example should include a different document mix, change class and approval/notification path.

## Decision after testing

Assess what was useful, confusing, missing or falsely precise. Decide whether to proceed to actual DOCX extraction, a first read-only document connection, relational persistence and authenticated roles. Technical completion alone does not approve any connection or external use.
