# Assumptions

- This is a standalone proposed service built from the methodology. It is neither a methodology update nor a resumption or replacement of the parked OPERATE Workspace MVP.
- Its user value is living documentation plus a connected operational knowledge base for bounded future AI monitoring and assistance.
- Many controlled documents may have an annual review cadence; the service should make evidence-led updates fast when required without treating every record as time-critical.
- Findings from service development and use may be submitted as evidence to the governed methodology-evolution process, but never applied automatically.
- All regulatory, organisation, customer, incident, evidence and approval examples are fictional demonstrations.
- A browser-local, resettable store is sufficient to prove workflow behaviour, but not durability or security.
- Entered approver names demonstrate the gate; they do not prove identity.
- One aggregate and one active user are sufficient for the first vertical slice.
- The repository's dependency-free architecture is the lowest-risk first milestone; TypeScript/React/Prisma is the documented migration target after value validation.
- Dates are fixed demo dates where repeatability helps; generated timestamps reflect runtime.
- Release `1.0` is seeded so the workflow demonstrates supersession into `1.1`.
- A material product decision, deployment, external publication or live integration still requires explicit approval from the authorised Operations Automated role.
- Confluence and Notion are first adapter tests, not privileged canonical stores or permanent limits on supported knowledge tools.
- Document platforms and action systems need different contracts: publishing a controlled view is not the same operation as creating or synchronising remediation work.
