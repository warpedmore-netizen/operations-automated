# Complete request framing, project routing and Codex handoff

## Jamie's direction

Jamie supplied a complete build brief requiring the AI Workbench to accept an ordinary-language need and determine the outcome, product, controlled context, classification, material questions, work hierarchy, readiness, minimum linked records, model or tool route and complete Codex handoff when implementation is genuinely ready.

The brief explicitly protects human control over purpose, scope, consequence and release. It requires existing answers and controlled context to be used before asking questions, separate projects to be identified before implementation, related Ideas to remain outside scope unless deliberately adopted and inadequate Codex returns to remain open. Jamie prohibited merge.

## AI interpretation

The current 1.8.0 proposal already contains the governed knowledge index, Product Purpose and Steering registries, project classifier, operational records, Work Profiles, Implementation Jobs and receipt validation. The material gap is the handoff between them: the Purpose & steering intake returns labels and a boundary recommendation but not a complete useful route.

The smallest coherent change is therefore a bounded request-framing module over the existing records and controls. It should enrich the existing steering intake, not introduce another canonical work system or replace specialist workflows.

## Evidence and limitations

- Recorded evidence: Jamie's supplied brief, current repository state, approved v0.7 Methodology, proposed Product Purpose and Steering artefacts, existing Workbench implementation and local operational-memory structures.
- AI inference: a distinct pure framing module with one additive intake extension is the least disruptive way to make the route reusable and testable.
- Limitation: deterministic text patterns and controlled retrieval support founder validation; they do not prove general-user interpretation quality.
- Authority: the current instruction authorises preparation on a proposal branch. It does not approve the proposed framing prompt, Product Purpose, Steering, merge, release or publication.

## Counter-tests

- **Only expand the existing classifier:** rejected because labels alone still leave the user to design the work package and Codex prompt.
- **Create every possible record automatically:** rejected because answer-only, Ideas, Methodology signals and purpose decisions require different minimum routes and authority.
- **Use a paid model for every intake:** rejected because simple classification and routing can be performed from controlled local context at no provider cost.
- **Send vague features to Codex:** rejected because stage D requires outcome, product, acceptance, recovery, authority and exact prompt provenance.
- **Create a new work-record hierarchy:** rejected because the Operations Bible and specialist stores already provide the governed records.

## Related Ideas review

There are existing ideas related to this area. Review them before finalising the scope.

`OA-IDEA-001` is relevant as a project-boundary test only. The Incident Management Simulation Game remains a separate Raw idea, and no new viability, impact, timing or commercial evidence justifies changing its status or adding it to this Workbench build.

## Disposition

Prepare a bounded Workbench product change on a layered proposal branch, reuse existing controlled context and record types, add the 16 required project-routing tests, verify the user journey and open a draft pull request. No Methodology meaning change is proposed.
