# AI Workbench governed base completion

## Status and purpose

This proposal completes the usable base journey for applying, challenging and evolving Operations Automated inside the private AI Workbench. It implements and proves product mechanics. It does not approve the proposed Workbench purpose, Methodology learning-system extension, Methodology–Workbench contract, Methodology meaning, merge, product release, Confluence Live promotion or external use.

The base is one vertical journey, not a collection of screens:

> challenge → grounded answer → correction → structured retention → related memory → counter-test → disposition → synthesis → proposed change → assurance → preparation Decision → Codex implementation → evidence review → release Decision → merge receipt → repository reindex → controlled publication where applicable → later approved-version use → outcome review → retained learning

## Preserved operating model

- Git remains authoritative for approved Methodology and governed meaning.
- SQLite remains authoritative for local conversations, work, feedback, corrections, Decisions, Approvals, Implementation Jobs, receipts and outcomes.
- Oppa Mate remains the recognisable Operations Automated AI service-account identity.
- Codex remains the implementation worker and source-code builder.
- The Workbench is the private place for ordinary work, review, correction and approval.
- Confluence retains controlled Draft and Live separation; Draft publication cannot approve meaning.
- AI may analyse, connect, recommend and perform authorised bounded mechanics. It cannot approve, merge, publish to Live, spend, accept risk or create authority.

## Completed base experiences

### Ask and apply

Material answers retain the exact approved Methodology baseline, component identifiers, knowledge snapshot, context, evidence, assumptions, uncertainty, result, options, recommendation, human authority, case test and feedback route. Approved sources remain normative; proposed and external material remains evidence.

### Challenge and retain

Every material feedback signal can retain:

- original wording and source;
- originating conversation and work context;
- strongest contextual meaning and AI interpretation;
- what changed in the assessment;
- uncertainty or disagreement;
- proportionate counter-test;
- evidence, limitations and confidentiality boundary;
- affected product and Methodology components;
- related signals and accepted correction;
- contradictions, confidence and visible disposition;
- disposition reason and named review trigger;
- Decision, implementation and final-outcome links.

The visible dispositions cover answer-only correction, conversation context, reusable correction, already covered, clarification, example or guidance, more evidence, Methodology change, product change, separate-project candidate, deferred, rejected, superseded, urgent review and no further action.

### Learn and synthesise

The **Methodology learning** area projects structured records and the current repository index. It directly answers:

- **What have you learned from me that has not yet been dealt with?**
- **Which approved Methodology changes came from my feedback?**

It shows unresolved signals, related-signal clusters, syntheses, clarification or guidance needs, proposed Methodology changes, awaiting evidence, awaiting human Decision, human-authorised releases, rejected or deferred positions and outcome reviews.

A Methodology Learning Review shows the signals, sources, corrections, current approved baseline, what is covered, unclear or possibly missing, contradictions, evidence strength, counter-evidence, contextual limits, proposed disposition, strongest no-change case, recommendation and exact human Decision or evidence required. The review remains proposed analysis.

### Manage connected work

The base continues to use Case, Request, Task, Incident, Problem, Change, Risk, Finding, Improvement, Scenario Test, Decision and Approval. It does not add a new canonical record type. Methodology learning, specialist histories and Implementation Jobs are projected into My Work where a human or AI action is genuinely required.

### Prepare and implement change

The complete Codex Implementation Job now contains:

- readable work reference, repository and proposal branch;
- Product Purpose, Steering and exact approved-prompt provenance;
- source request, intended outcome and user problem;
- relevant evidence, current behaviour and required behaviour;
- in-scope requirements and explicit exclusions;
- data, security and architecture constraints;
- affected components, acceptance criteria and test scenarios;
- migration, rollback and documentation requirements;
- unresolved questions and exact authority boundary; and
- the structured return format.

The Codex return contains the work reference, branch, pull request, commit, changed files, implemented behaviour, tests, validation, migration, rollback, unresolved risks, evidence for every acceptance criterion, remaining work and version impact.

An incomplete or failed return receives no release-ready state. The Build Job remains open and the missing acceptance evidence is returned to Codex. A complete receipt still requires a separate founder release Decision and exact merge receipt.

## Migration and recovery

SQLite migration 9 is additive and idempotent. It extends feedback records without deleting or replacing conversations, feedback, Decisions, Approvals, Brand Review, Confluence history, Implementation Jobs, operational records, snapshots or audit history.

The automated vertical fixture takes a consistent pre-change SQLite backup while the Workbench is running, completes the release-and-outcome route, then opens the backup as a test restoration copy and verifies that the pre-change conversations and feedback remain readable and that no later release has leaked into it. The fixture also restores the pre-change approved repository artefact into a test copy and verifies exact equality.

Operational recovery remains the paired route:

1. stop the local Workbench;
2. retain the failed database and application commit for evidence;
3. restore the last verified SQLite copy and prior application commit in a test location;
4. verify retained record counts and authority states;
5. replace the active local copy only through a separately authorised recovery action; and
6. retain the failure and recovery evidence.
