# AI and agent operational assurance and value case 001

## Purpose

Use one bounded, non-confidential operation to test whether RP-01 and RP-02 create a better operational decision without excessive record burden.

The selected operation is the internal Operations Automated methodology-development loop: founder direction or operational feedback enters an AI-led repository workflow and should leave as a useful answer, retained disposition, decision-ready proposal where justified, and later outcome evidence. The case uses the current repository, GitHub pull-request state, local Workbench behaviour and non-confidential founder direction only.

## Minimum founder input

The original minimum input contract asked Jamie to supply five items. Jamie's 2026-08-24 direction to continue the previously recommended next steps authorised the case to proceed. The controlled record already contained enough evidence to reconstruct the minimum inputs without transferring the analytical work back to Jamie:

1. **Operation:** challenge or request through analysis, retained feedback, proposal, human decision, release and outcome review.
2. **Primary person and outcome:** Jamie receives useful, decision-ready methodology development quickly without having to operate developer tooling.
3. **AI or agent action:** retrieve, analyse, challenge, draft, check, create branches, commit, push and open draft pull requests within the recorded boundaries.
4. **Material failure or harm:** unapproved meaning or consequence is treated as authorised; work is produced without user value; feedback is reported as dealt with while the decision route remains incomplete; or accumulated work obscures the next governed action.
5. **Baseline and authority:** the repository, current pull requests, Workbench records, local automation state and this facilitated run provide the baseline. Jamie retains methodology meaning, merge, release, publication, spending, risk acceptance, external contact and delegated-authority decisions.

No employer, client, customer, employee or third-party confidential information was requested or used.

## Scope and exclusion

Included: journey, outcome, owner, delegation, runtime assurance, baseline, full cost, value, failure, recovery and the next governed decision.

Excluded: production connection, new provider access, credentials, personal monitoring, external contact, spending, risk acceptance, methodology approval, product build and publication.

## Case record

### Direction and boundaries

- **Operation/workflow:** Operations Automated methodology-development and governed change loop.
- **Primary person and journey:** Jamie gives direction or feedback in ordinary language; AI returns useful progress, retains material learning and prepares only the decisions Jamie must make.
- **Outcome and minimum acceptable outcome:** A useful provisional answer and unambiguous next action now; traceable disposition, evidence and authority for material change; no inferred approval.
- **People affected:** Jamie during founder validation; future practitioners and users if the resulting method is later approved and released.
- **Operational owner:** Jamie Peppard during the founder-controlled phase; AI manages authorised routine preparation.
- **Decision authority:** Jamie Peppard for methodology meaning and the consequential boundaries recorded above.
- **Information boundary:** Non-confidential only

### Evidence separation

- **Recorded evidence:** Approved v0.7 sources; AGENTS.md; the four open GitHub proposals; current branch and commit history; the user-local Workbench database copied for read/write-safe inspection; Workbench API projections; the paused local AI-owner automation; and the 2026-08-24 founder direction.
- **Jamie's judgement:** AI should continue doing authorised work rather than stop at instructions telling Jamie to follow a process; the development system should move quickly and converge on something useful for people.
- **AI inference:** The main constraint is decision and evidence flow, not missing repository or Workbench capability.
- **Assumptions:** "Keep on going" authorises reversible, governed preparation but not merge, release, publication, external contact, spending, risk acceptance or broader delegation.
- **Recommendation:** Retain AI-led development as a bounded experiment, reduce open decision work, measure complete learning outcomes and test the smallest useful output with an independent person before further product expansion. This is not approval.

## Provisional operational assessment

### Primary journey and operational value system

The first visible event is Jamie expressing a need, correction or challenge. The minimum useful service is not a document or pull request: it is a response that helps Jamie understand, decide or progress. The supporting operation then retrieves the approved baseline, frames the issue, produces a provisional answer, captures material feedback, tests related evidence, assigns a visible disposition and either closes the learning route or prepares a decision-ready proposal. A later approved release must be reapplied and outcome-reviewed.

The operation currently has strong preparation mechanics but weak completion evidence. On 2026-08-24:

- GitHub showed four open proposals, with no open proposal updated after 2026-08-02;
- the current Workbench projected one cluster containing 11 retained signals but no confirmed Methodology component;
- the Workbench summary said every signal had an explained disposition and reported zero items awaiting human decision, while the same cluster carried a `methodology-change-candidate` disposition and asked Jamie to decide whether to prepare, revise, defer or reject a proposal;
- no Workbench-traced human-authorised Methodology release or outcome review existed;
- the AI-owner queue contained no ready work, so its paused heartbeat created no current service loss; and
- the daily methodology challenge existed as a due My Work item after 08:00 without a separate Codex scheduled automation.

This shows that retained information and technical routing do not yet equal an operationally completed learning cycle.

### Readiness position

- **Operationally ready for a bounded facilitated case:** yes. Purpose, owner, authority, sources and recovery are identifiable.
- **Automation-ready:** partly. Deterministic Workbench projections and Git mechanics are useful, but completion semantics need correction.
- **AI-ready:** yes for analysis and reversible preparation within the controlled repository; outcome quality still requires Jamie's critique.
- **Agentic-ready:** only for bounded preparation. Runtime trace is fragmented across the Codex task, Git, GitHub, Workbench and automation record. Merge, release and other consequential boundaries rely partly on instructions and human restraint rather than proved technical enforcement.
- **Ready to scale or expose to external users:** no. Independent activation, full cost, support burden, outcome evidence, security and external-use decisions remain missing.

### RP-01 finding

The profile exposed a material decision that ordinary project instructions alone did not make as visible: the current operation is suitable for bounded AI preparation but not for unattended consequential execution. It also exposed fragmented runtime evidence and the absence of proved technical enforcement for some human gates.

The full twenty-section guide was too large for first use. The short profile above contained the fields that changed the decision. RP-01 should therefore add a mandatory short first-use card and keep the deeper profile as consequence-led expansion. It remains Proposed C2 until a non-author uses it.

- Material action can be reconstructed from proportionate runtime evidence.

## RP-02 acceptance evidence

- Material inclusion and discovery rules are understandable.
- Baseline and AI-enabled outcomes are comparable with stated uncertainty.
- Full cost per accepted outcome is usable or a defensible range/limitation is recorded.

- The owner can maintain the minimum record.

## Measures

- time to first useful finding;
- clarification effort and inaccessible language;
- number of fields removed or added after use;
- material authority, failure or value gaps exposed;
- whether the evidence changes a decision;
- owner confidence with reasons, not a maturity score; and
- activation: whether the intended user can begin without repository or developer knowledge.

## Case decision and learning

- **Operational recommendation:** Retain the AI-led methodology-development loop as a bounded founder experiment; reduce decision WIP; correct contradictory completion semantics; measure accepted outcome units, end-to-end time and founder effort; and run the resulting smallest aid with an independent person before scaling or building further product capability.
- **Authority required:** Jamie critiques this assessment and later decides RP-01 and RP-02 separately. Any merge, private Workbench release, external participant, publication or wider delegation remains separately governed.
- **RP-01 disposition:** Revise proposed supporting guidance from case evidence; retain Proposed C2.
- **RP-02 disposition:** Revise proposed supporting guidance from case evidence; retain Proposed C2.
- **Core methodology change:** No change proposed. Approved v0.7 already requires user-defined value, proportionate readiness, human authority, recovery, actionable output and outcome-led learning. The observed gaps concern supporting guidance, product completion semantics and operational execution.
- **Product feedback:** A learning cluster that still recommends a human methodology decision must not be summarised as fully dealt with or excluded from decision counts merely because each source signal has a stored disposition.
- **Activation learning:** A local database path can be technically present but unusable in the executing environment. The isolated copy proved a safe fallback and stop/restart route; the ordinary launch path remains unverified in this execution environment.
- **Review trigger:** Jamie's critique, one independent first-use test, a corrected Workbench learning projection or an earlier material failure.
